### Workout pipeline — stuck-post root-cause analysis (Phase 4 mandate)

Path: Upload → `createPost` (PENDING) → `after()` → classify (3× retry, backoff
1s/4s/16s) → VERIFIED tx (post flip + event + streak, atomic) or REJECTED.

Every scenario that produces the "This is taking a moment…" stuck state:

1. **after() dropped** (instance reclaimed) → post stays PENDING.
   → *Recovered by reconciler since 2026-06-12.* ✅
2. **AI retries exhausted** (provider outage) → PENDING + `AI_CLASSIFICATION_FAILED` event.
   → *Recovered by reconciler.* ✅
3. **Verify transaction rollback** (e.g. DailyCompletion race) → PENDING by design.
   → *Recovered by reconciler.* ✅
4. **Reconciler itself dead** — was the case until today (`http://` 308 bug, now fixed,
   documented in CLAUDE.md §18). ✅
5. **Poison post** — an image that *always* fails classification is retried by the
   reconciler **forever, every cron run** (no attempt cap, no dead-letter). ⚠ **H1 — only remaining stuck scenario.**

## 3. Critical Issues

### C1 — Upstash rate limiter does not enforce configured limits  ⚠ SECURITY
- **File:** `server/core/middleware/rateLimit.ts:28-34, 70-91`
- **Root cause:** One shared `Ratelimit` instance hardcoded to
  `slidingWindow(100, '1 m')`. Per-call `maxRequests/windowMs` are embedded **in
  the key string only** — they namespace the counter but the *limit* is always
  100/min. The intended limits are enforced only by the in-memory fallback,
  which is per-serverless-instance (i.e. unreliable, and only after Upstash has
  already said "allow").
- **Impact:** In production: login = 100/min/IP (designed: 5/min) → credential
  stuffing; signup = 100/min (designed: 3/min); posts/create = 100/min/user
  (designed: 5/hr) → AI quota/cost abuse + DailyCompletion hammering; uploads/sign
  = 100/min (designed: 10/hr) → R2 abuse.
- **Probability:** Certain (every prod request takes this path).
- **Fix:** Cache one `Ratelimit` instance **per config** in a
  `Map<string, Ratelimit>` keyed `${maxRequests}:${windowMs}`, constructing
  `Ratelimit.slidingWindow(config.maxRequests, msToUpstashWindow(config.windowMs))`
  for each. Remove the double-enforcement (skip memCheck when Upstash answered).
  Extend `tests/unit/` coverage with a mocked Ratelimit asserting per-config limits.

## 4. Reliability Findings (High → Medium)

### H1 — Poison-post infinite retry in reconciler
`reprocessStalePendingPosts` retries any PENDING post older than 2 min on every
cron run, forever. A post whose image consistently fails classification burns
3 Gemini calls + up to 21s per run, indefinitely.
**Fix:** count reconcile attempts (either a `classificationAttempts` column on
Post, or count `AI_CLASSIFICATION_FAILED` events per postId) and after N (e.g. 5)
total failures mark the post REJECTED with reason `classification_unavailable`
(+ notification to user to re-upload). Keeps "AI never decides" intact — this is
an operational timeout, not an AI decision.

### H2 — Duplicate + ignored cron configuration
- Root `vercel.json` crons are **silently ignored** (Vercel Root Directory =
  `app/web`) — pure confusion.
- `app/web/vercel.json` schedules streak-evaluator daily 23:00 **and**
  cron-job.org runs it hourly → double execution at 23:00. Idempotency keys make
  this harmless today, but it's two sources of truth.
**Fix:** delete the `crons` block from root `vercel.json` (keep the comment),
decide one trigger for streak-evaluator (recommend: keep cron-job.org hourly,
delete the Vercel cron entry), and document both jobs in `docs/DEPLOYMENT.md`
(including the **https:// requirement**).

### H3 — Reconciler can exceed maxDuration mid-batch
Worst case: 10 posts × ~21s retry budget each ≈ 210s > `maxDuration = 60`.
Function killed mid-batch; idempotent so no corruption, but the same failing
posts retry next run and the run reports nothing.
**Fix:** reduce default `RECONCILE_BATCH_LIMIT` to 3, or add an elapsed-time
budget check (`if (Date.now() - start > 45_000) break`) in the loop. One-line-ish.

### M1 — Story pre-render droppable; FAILED rows never retried
`void generateAndPersistStory(...)` inside after() may be dropped when the
invocation ends. Mitigated by on-demand render in the read path (user-visible
impact: first share tap is slow, not broken). FAILED rows are permanent.
**Fix (low priority):** have the existing reprocess-pending cron route also call a
`retryFailedStories(limit)` service fn, or simply accept on-demand rendering as
the retry. Decide; document.

### M2 — In-memory limiter quirks
Unbounded `_memStore` Map (slow leak on warm instances/dev) and double-counting
(memCheck runs even after Upstash allowed). Fold into the C1 rewrite: skip
memCheck when Upstash is configured; add a periodic sweep or size cap to the Map.

### M3 — `getSession()` revocation window
Revoked tokens valid up to ~1h. Documented, deliberate, acceptable for MVP.
**Action:** none; revisit at launch review.

### M5 — No alerting on cron failures
The reprocess cron was dead for days and nothing alerted. cron-job.org supports
failure notification emails; Sentry supports Cron Monitors (check-ins).
**Fix:** enable cron-job.org failure notifications (manual, 2 min) and/or add
Sentry check-ins to both cron routes.
